# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.3 Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

Для аналізу обрано три програмні системи вторинного обігу квитків: Ticketmaster (Fan-to-Fan Resale), StubHub та TicketSwap. Внутрішня архітектура зазначених систем не є відкритою, тому опис сформовано за публічними джерелами: технічними кейсами вендорів, вакансіями інженерних команд, офіційними заявами компаній та матеріалами розслідувань інцидентів. Параметри, відомості про які публічно не розкриваються, позначено відповідно.

### 1.3.1 Ticketmaster (Fan-to-Fan Resale)

**Архітектурний патерн.** Об'єктом аналізу є вбудований вторинний ринок Fan-to-Fan Resale, що функціонує на спільній платформі з первинним продажем. Платформа є розподіленою системою із сотень програмних систем і компонентів, що перебуває в процесі міграції на мікросервісну архітектуру. Центральним інтеграційним шаром є платформа потокової обробки подій на базі Apache Kafka (Confluent Platform), через яку проходять дані всіх систем. Потік інвентарю (доступність місць, ціни, пакети) маршрутизується в окремі сховища під різні сценарії використання. Подієва шина знижує зв'язність між системами та дозволяє масштабувати споживачів незалежно, проте зростання кількості технологій ускладнює моніторинг.

**Протоколи передачі даних.** REST API для зовнішніх партнерів; асинхронний обмін подіями через Apache Kafka між внутрішніми системами; окремий API рендерингу квитка для мобільного застосунку.

**Стек даних і консистентність.** Конкретні СУБД транзакційного ядра публічно не розкриваються. Частина клієнтських даних зберігалася у хмарному сховищі даних Snowflake. Розподіл даних між кількома сховищами через потік подій забезпечує узгодженість у кінцевому підсумку (Eventual Consistency).

**Механізми безпеки.**
- SafeTix: штрихкод формату PDF417 містить статичний bearer-токен квитка та два TOTP-коди (SHA-1, крок 15 с), згенеровані з ключа події та ключа клієнта, і мітку часу.
- Verified Fan: попередня реєстрація покупців для відсіювання автоматизованого трафіку.
- ML-моделі для виявлення облікових записів, що отримують пріоритетний доступ з метою подальшого перепродажу.

**Технічні обмеження (Technical Bottlenecks).**
- Пікове навантаження: під час передпродажу туру Eras Tour (листопад 2022) система отримала 3,5 млрд запитів, що вчетверо перевищило попередній пік. Значну частку трафіку становили боти. Близько 15 % користувачів зазнали затримок і помилок валідації кодів доступу; частина квитків втрачалася з кошика.
- Безпека облікових записів інфраструктури: у травні 2024 року зафіксовано несанкціонований доступ до бази даних у Snowflake. Атака була спрямована на облікові записи з однофакторною автентифікацією та використовувала викрадені облікові дані. Зловмисники заявили про 560 млн записів користувачів.
- SafeTix: bearer-токен кешується на пристрої для офлайн-відображення, що створює можливість копіювання даних квитка.

### 1.3.2 StubHub

**Архітектурний патерн.** Великомасштабне середовище із сотень сервісів і баз даних. Застосовуються мікросервіси та подієво-керовані (Event-Driven) сервіси. Історично ядро даних побудовано на монолітних сховищах Microsoft SQL Server, які наразі декомпозуються на спеціалізовані системи зберігання. Мови розробки: C#, Java, C++.

**Протоколи передачі даних.** Асинхронна взаємодія через черги повідомлень з інфраструктурою повторних спроб (retry) і версіонуванням повідомлень. Протоколи синхронної взаємодії сервісів публічно не розкриваються.

**Стек даних і консистентність.**
- Microsoft SQL Server як основна СУБД.
- Key-value сховища, розподілені кеші, blob-сховище.
- Транзакційна консистентність у межах SQL Server; між сервісами — асинхронна узгодженість через черги повідомлень.

**Механізми безпеки.** Механізми перевірки автентичності квитків і захисту від автоматизованого трафіку публічно не документуються.

**Технічні обмеження (Technical Bottlenecks).**
- Монолітні сховища SQL Server створюють жорстку зв'язність даних і обмежують незалежне масштабування сервісів; їх декомпозиція є окремим інженерним напрямом компанії.
- Робота з продуктивністю SQL Server (тюнінг запитів, індексів, планів виконання) виділена в окрему спеціалізацію, що свідчить про навантаження на централізовану СУБД як на вузьке місце.

### 1.3.3 TicketSwap

**Архітектурний патерн.** Тип декомпозиції публічно не описано. За технологічним стеком: серверний застосунок на PHP (Symfony) з асинхронною обробкою задач через RabbitMQ, клієнтські застосунки на React / Next.js та нативні мобільні застосунки (iOS, Android), розгортання в контейнерах під керуванням Kubernetes.

**Протоколи передачі даних.** GraphQL API; асинхронний обмін через брокер повідомлень RabbitMQ.

**Стек даних і консистентність.**
- MySQL як реляційна СУБД.
- Redis як In-Memory сховище.
- Elasticsearch для повнотекстового пошуку.
- Транзакційна консистентність у межах MySQL; пошуковий індекс Elasticsearch оновлюється асинхронно.

**Інфраструктура.** AWS, Kubernetes, Terraform (Infrastructure as Code).

**Механізми безпеки.** SecureSwap — інтеграція з системами квиткових операторів (Paylogic, Easol, Stager та ін.): після перепродажу оригінальний штрихкод анулюється, генерується новий, і покупцю видається новий квиток.

**Технічні обмеження (Technical Bottlenecks).**
- Гарантія автентичності SecureSwap діє лише для подій, організатори яких використовують інтегрованих квиткових операторів. Для решти подій перевипуск квитка неможливий, і ризик повторного продажу одного квитка зберігається.
- Залежність ключового механізму безпеки від зовнішніх API третіх сторін: кожна нова інтеграція потребує окремої розробки та підтримки.

### 1.3.5 Висновки до підрозділу

Аналіз показав, що в усіх трьох аналогах вирішальні механізми безпеки або винесені за межі платформи, або обмежені масштабом інтеграцій. У Ticketmaster захист від автоматизованого трафіку побудовано на попередній реєстрації покупців і чергах очікування, що не запобігло відмовам під час піку у 3,5 млрд запитів, а компрометація хмарного сховища даних стала можливою через однофакторну автентифікацію службових облікових записів. У TicketSwap гарантія автентичності квитка залежить від наявності інтеграції з квитковим оператором організатора і для решти подій відсутня. У StubHub централізовані монолітні сховища на Microsoft SQL Server формують жорстку зв'язність даних, декомпозиція якої виділена в окремий інженерний напрям.

З урахуванням виявлених обмежень у межах кваліфікаційної роботи передбачено перенесення захисних механізмів на рівень застосунку. Протидія автоматизованому трафіку реалізується алгоритмом Token Bucket (Bucket4j + Redis) з лімітами на рівні IP-адреси та облікового запису, а також квотою квитків на обліковий запис для однієї події. Подвійний продаж виключається двома незалежними рівнями блокування: розподіленим блокуванням у Redis з обмеженим TTL та оптимістичним блокуванням на рівні PostgreSQL. Автентичність квитка забезпечується перевипуском із QR-кодом, підписаним ECDSA, що не потребує інтеграції зі сторонніми операторами. Керування ідентичністю централізовано в Keycloak з обов'язковою двофакторною автентифікацією для облікових записів продавців. Від мікросервісної архітектури Ticketmaster та StubHub запозичено принцип асинхронної подієвої взаємодії, проте застосовано його в межах модульного моноліту з патерном Transactional Outbox, що гарантує доставку подій без розподілених транзакцій.

Обраний підхід містить архітектурний компроміс: модульний моноліт не забезпечує незалежного горизонтального масштабування окремих модулів, яке надає мікросервісна архітектура. Водночас він усуває мережеві затримки міжсервісних викликів, спрощує забезпечення транзакційної цілісності угоди та знижує операційну складність інфраструктури, а чітко визначені межі модулів зберігають можливість подальшого виділення модулів `payment` і `notification` в окремі сервіси. Визначені вимоги до відмовостійкості, безпеки та меж модулів є вихідними даними для проєктування архітектури системи в Розділі 2.

## 1.4 Аналіз обраної предметної області (модель As-Is)

### 1.4.1 Загальна характеристика домену

Предметною областю є вторинний обіг квитків на культурні, спортивні та розважальні заходи — передача права відвідування заходу від первинного покупця іншій особі за грошову винагороду. Вторинний ринок функціонує паралельно з первинним продажем і охоплює три типи каналів: неспеціалізовані канали (соціальні мережі, месенджери, дошки оголошень), спеціалізовані маркетплейси перепродажу (StubHub, TicketSwap) та вбудовані модулі перепродажу платформ первинного продажу (Ticketmaster Fan-to-Fan Resale).

Станом на 2026 рік у домені простежуються такі технологічні тенденції:

- перехід від друкованих квитків і статичних PDF-файлів до мобільних квитків, прив'язаних до облікового запису та застосунку;
- застосування динамічних штрихкодів, що періодично оновлюються на основі одноразових паролів (TOTP), як засобу протидії копіюванню квитка;
- перевипуск квитка при перепродажу з анулюванням попереднього штрихкоду через інтеграцію з квитковим оператором;
- попередня верифікація покупців і віртуальні черги очікування як засоби протидії автоматизованому трафіку під час пікових продажів;
- застосування подієво-керованих архітектур та платформ потокової обробки подій для синхронізації інвентарю між системами.

### 1.4.3 Бізнес-процеси та Workflows (As-Is)

**Процес 1. Розміщення та верифікація квитка.**

У неспеціалізованих каналах продавець публікує зображення квитка або PDF-файл у текстовому повідомленні. Потік даних не проходить через жодний сервіс перевірки: штрихкод передається покупцю у відкритому вигляді до або після оплати. На спеціалізованих платформах продавець завантажує файл квитка через API, після чого сервер зберігає штрихкод і публікує оголошення. Перевірка автентичності виконується лише за наявності інтеграції з квитковим оператором (наприклад, SecureSwap у TicketSwap); для решти подій перевірка обмежується валідацією формату файлу.

Вузькі місця (bottlenecks):

- один і той самий штрихкод може бути опублікований у кількох каналах одночасно, оскільки відсутній спільний реєстр опублікованих штрихкодів;
- штрихкод зберігається та передається у відкритому вигляді, тому його копіювання до завершення угоди не контролюється;
- верифікація залежить від зовнішнього API оператора, тож для подій без інтеграції ризик повторного продажу зберігається.

**Процес 2. Купівля квитка в умовах конкурентного доступу.**

Клієнт надсилає HTTP-запит на придбання оголошення; сервер зчитує статус оголошення з бази даних, перевіряє його доступність і записує новий статус. За відсутності блокування між операціями читання та запису (патерн check-then-act) два паралельні запити можуть одночасно отримати статус «доступно», що призводить до подвійного продажу (race condition). Під час пікових продажів автоматизовані клієнти генерують запити з частотою, що значно перевищує людську, та резервують інвентар без завершення оплати (загроза OAT-021 Denial of Inventory), а також скуповують квитки для подальшого перепродажу (OAT-005 Scalping).

Вузькі місця (bottlenecks):

- race condition між читанням і записом статусу оголошення;
- відсутність обмеження частоти запитів на рівні IP-адреси та облікового запису;
- відсутність обмеженого в часі резерву: незавершене замовлення утримує квиток необмежено довго або не утримує зовсім;
- пікове навантаження на синхронний шлях запиту до бази даних, що збільшує затримку (Latency) та кількість відмов; під час передпродажу Eras Tour (2022) платформа Ticketmaster отримала 3,5 млрд запитів, а близько 15 % користувачів зазнали затримок і помилок.

**Процес 3. Розрахунок та передача квитка.**

У неспеціалізованих каналах покупець здійснює передоплату прямим переказом, після чого продавець надсилає файл квитка; гарантія виконання угоди відсутня для обох сторін. На спеціалізованих платформах оплата проходить через платіжного провайдера, проте зміна стану замовлення, передача квитка та сповіщення сторін виконуються послідовними синхронними викликами. У разі збою на одному з кроків (недоступність поштового сервісу, помилка оператора) стани замовлення, платежу та квитка можуть розійтися, а відновлення потребує ручного втручання.

Вузькі місця (bottlenecks):

- відсутність формалізованої моделі станів замовлення та явного утримання коштів до передачі квитка;
- синхронна послідовність викликів без гарантованої доставки подій: збій сповіщення або запису журналу втрачає подію;
- відсутність незмінного журналу аудиту, необхідного для розгляду спірних ситуацій.

### 1.4.4 Регуляторні та індустріальні обмеження

- **Захист персональних даних:** Регламент (ЄС) 2016/679 (GDPR) та Закон України «Про захист персональних даних» — принцип мінімізації даних, законна підстава обробки, право на видалення.
- **Платіжні дані:** стандарт PCI DSS — зберігання та обробка даних платіжних карток допускається лише в сертифікованому середовищі; за межами платіжного провайдера дані карток не зберігаються.
- **Протидія ботам:** класифікація OWASP Automated Threats to Web Applications (OAT-005 Scalping, OAT-021 Denial of Inventory); у США — Better Online Ticket Sales Act (BOTS Act, 2016), що забороняє обхід технічних обмежень продажу квитків автоматизованими засобами.
- **Безпека застосунку:** OWASP Top 10 як базовий перелік класів вразливостей веб-застосунків.
- **Автентифікація:** OAuth 2.0 (RFC 6749), OpenID Connect Core 1.0, TOTP (RFC 6238).
- **Криптографія:** алгоритм цифрового підпису ECDSA згідно з FIPS 186-5.

## 1.5 Постановка задачі та формування вимог

### 1.5.1 Концептуальна модель To-Be

Розроблювана платформа переносить захисні механізми трьох ключових процесів на рівень застосунку та замінює синхронні ланцюжки викликів подієвою взаємодією модулів.

**Процес 1 (To-Be). Розміщення квитка.** Запит продавця проходить автентифікацію через Keycloak (OIDC) з обов'язковою двофакторною автентифікацією для ролі продавця. Модуль `listing` обчислює SHA-256 хеш штрихкоду, перевіряє його унікальність за унікальним індексом PostgreSQL і відхиляє дублікат на рівні бази даних. Ціна перепродажу перевіряється відносно номінальної вартості. Відкритий штрихкод не зберігається.

**Процес 2 (To-Be). Резервування та купівля.** Запит покупця спочатку проходить обмеження частоти (Token Bucket, Bucket4j + Redis) на рівні IP-адреси та облікового запису і перевірку квоти квитків на подію. Модуль `order` встановлює розподілене блокування оголошення в Redis з TTL резерву; запис у PostgreSQL виконується з оптимістичним блокуванням (`@Version`). Конкурентний запит отримує відмову без звернення до бази даних. Після завершення TTL резерв звільняється автоматично. Таким чином, race condition усувається двома незалежними рівнями, а автоматизований трафік відсікається до бізнес-логіки.

**Процес 3 (To-Be). Розрахунок і передача.** Замовлення проходить через скінченний автомат станів `CREATED → PAID → TICKET_REISSUED → COMPLETED / CANCELLED`. Кошти утримуються до переходу у стан `TICKET_REISSUED`. Після оплати попередній QR-код анулюється, а покупцю видається новий квиток із QR-кодом, підписаним ECDSA. Кожна зміна стану записується в таблицю outbox у тій самій транзакції, що й зміна бізнес-даних (Transactional Outbox), і доставляється в RabbitMQ; модулі `audit` та `notification` обробляють події ідемпотентно. Збій сповіщення не впливає на стан угоди, а подія доставляється повторно.

### 1.5.2 Функціональні вимоги (Core Features)

**Модуль `identity`**
- Автентифікувати користувачів через Keycloak за протоколом OpenID Connect та розмежовувати доступ за ролями «покупець», «продавець», «адміністратор» (RBAC).
- Вимагати двофакторну автентифікацію (TOTP) для облікових записів з роллю «продавець».
- Обмежувати частоту запитів за алгоритмом Token Bucket на рівні IP-адреси та облікового запису і тимчасово блокувати облікові записи з аномальною активністю.

**Модуль `listing`**
- Реєструвати квиток зі збереженням SHA-256 хешу штрихкоду, відхиляти дублікати та перевіряти обмеження ціни перепродажу відносно номінальної вартості.

**Модуль `order`**
- Резервувати квиток з розподіленим блокуванням у Redis (TTL) та оптимістичним блокуванням у PostgreSQL, обмежувати кількість квитків на обліковий запис для однієї події та автоматично звільняти резерв після завершення TTL.
- Керувати станами замовлення через скінченний автомат з утриманням коштів до перевипуску квитка (платіжний шлюз — заглушка зі стабільним контрактом).

**Модуль `ticket`**
- Перевипускати квиток з анулюванням попереднього QR-коду, підписувати новий QR-код алгоритмом ECDSA та надавати ендпоінт верифікації підпису.

**Модулі `audit` та `notification`**
- Публікувати зміни станів угод і події безпеки через Transactional Outbox у RabbitMQ, записувати їх у append-only журнал аудиту та надсилати email-сповіщення сторонам угоди; приймати звернення щодо проблемного квитка через форму з відповіддю на email.

### 1.5.4 Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка захищеної веб-платформи перепродажу квитків з архітектурою модульного моноліту та подієвою взаємодією модулів для вирішення задачі безпечного вторинного обігу електронних квитків в умовах конкурентного доступу та автоматизованого трафіку. Для досягнення мети передбачено реалізацію двох незалежних рівнів блокування для виключення подвійного продажу, обмеження частоти запитів за алгоритмом Token Bucket та квот на обліковий запис, перевипуску квитка з криптографічним підписом ECDSA, керування ідентичністю на основі OpenID Connect з двофакторною автентифікацією та гарантованої доставки подій за патерном Transactional Outbox. Відповідність системи вимогам NFR-01 – NFR-18 підлягає перевірці засобами навантажувального тестування (k6) та інструментального аудиту безпеки в конвеєрі CI/CD.
