## 1. System Context (Контекст системи)

### 1.1 Призначення та межі системи (Scope)

Система призначена для вторинного обігу електронних квитків на культурні, спортивні та розважальні заходи: розміщення квитка продавцем, резервування та оплата квитка покупцем, перевипуск квитка з криптографічним підписом і перевірка автентичності квитка на вході.

**У межах системи:**
- автентифікація та авторизація користувачів (Keycloak, OpenID Connect);
- захист від автоматизованого трафіку (обмеження частоти запитів, квоти);
- каталог подій та оголошень;
- розміщення квитка з контролем дублікатів і обмеженням ціни;
- резервування квитка з виключенням подвійного продажу;
- керування станами замовлення з утриманням коштів;
- перевипуск квитка з QR-кодом, підписаним ECDSA, і верифікація підпису;
- журнал аудиту та email-сповіщення;
- прийняття звернень щодо проблемного квитка.

**За межами системи:**
- інтеграція з системами квиткових операторів організаторів;
- реальне проведення платежів (платіжний провайдер реалізовано як заглушку зі стабільним контрактом);
- розгляд спорів (приймається лише звернення з відповіддю на email після розгляду);
- нативні мобільні застосунки.

### 1.2 Актори та зовнішні системи

| Елемент | Тип | Взаємодія з системою |
|---|---|---|
| Покупець (BUYER) | Користувач | Перегляд каталогу, резервування, оплата, отримання квитка |
| Продавець (SELLER) | Користувач | Розміщення квитка, отримання коштів |
| Адміністратор (ADMIN) | Користувач | Модерація оголошень, керування блокуваннями, перегляд журналу аудиту |
| Система контролю входу на заході | Зовнішня система | Перевірка підпису QR-коду через REST API |
| Платіжний провайдер (заглушка) | Зовнішня система | Утримання, списання та повернення коштів через REST API |
| SMTP-сервер | Зовнішня система | Доставка email-сповіщень |

### 1.3 Обмеження середовища

- Цільове середовище розгортання: один віртуальний сервер (VPS) з ресурсами 2 vCPU / 4 GB RAM.
- Усі компоненти розгортаються в Docker-контейнерах засобами Docker Compose.
- Мова реалізації серверної частини: Java 21 (Spring Boot 3); клієнтської частини: TypeScript (React).

## 2. Functional Requirements (Функціональні вимоги)

### 2.1 Модуль `identity`

#### SRS-FUN-01
Система повинна автентифікувати користувачів через Keycloak за протоколом OpenID Connect (Authorization Code Flow з PKCE).

#### SRS-FUN-02
Система повинна авторизувати доступ до кожного ендпоінту API на основі ролей BUYER, SELLER та ADMIN, переданих у JWT-токені (RBAC).

#### SRS-FUN-03
Система повинна вимагати двофакторну автентифікацію (TOTP) під час входу користувачів з роллю SELLER.

#### SRS-FUN-04
Система повинна обмежувати частоту запитів до API за алгоритмом Token Bucket окремо для кожної IP-адреси.

#### SRS-FUN-05
Система повинна обмежувати частоту запитів на резервування за алгоритмом Token Bucket окремо для кожного облікового запису.

#### SRS-FUN-06
Система повинна тимчасово блокувати обліковий запис, що перевищив ліміт частоти запитів у кількості, визначеній [SRS-NFR-SEC-08](#srs-nfr-sec-08).

#### SRS-FUN-07
Система повинна надавати адміністратору можливість розблокувати обліковий запис.

### 2.2 Модуль `catalog`

#### SRS-FUN-08
Система повинна надавати перелік подій та активних оголошень з пагінацією та фільтрацією за датою і місцем проведення.

### 2.3 Модуль `listing`

#### SRS-FUN-09
Система повинна зберігати штрихкод квитка виключно у вигляді хешу SHA-256.

#### SRS-FUN-10
Система повинна відхиляти розміщення квитка, хеш штрихкоду якого вже зареєстровано.

#### SRS-FUN-11
Система повинна відхиляти розміщення оголошення з ціною, що перевищує номінальну вартість квитка більш ніж у конфігурований коефіцієнт (значення за замовчуванням — 1,2).

#### SRS-FUN-12
Система повинна надавати адміністратору можливість деактивувати оголошення.

### 2.4 Модуль `order`

#### SRS-FUN-13
Система повинна резервувати оголошення для одного покупця на час TTL і відхиляти одночасні спроби резервування того самого оголошення іншими покупцями.

#### SRS-FUN-14
Система повинна відхиляти резервування, якщо кількість квитків облікового запису для однієї події досягла квоти, визначеної [SRS-NFR-SEC-07](#srs-nfr-sec-07).

#### SRS-FUN-15
Система повинна автоматично звільняти резерв після завершення TTL, якщо оплату не підтверджено.

#### SRS-FUN-16
Система повинна виконувати зміну стану замовлення лише за дозволеними переходами скінченного автомата: `CREATED → PAID → TICKET_REISSUED → COMPLETED`, `CREATED → CANCELLED`, `PAID → CANCELLED`.

#### SRS-FUN-17
Система повинна утримувати кошти покупця до переходу замовлення у стан `TICKET_REISSUED` і ініціювати повернення коштів при переході зі стану `PAID` у стан `CANCELLED`.

### 2.5 Модуль `ticket`

#### SRS-FUN-18
Система повинна анулювати попередній QR-код квитка після переходу замовлення у стан `PAID`.

#### SRS-FUN-19
Система повинна формувати для покупця новий QR-код, підписаний алгоритмом ECDSA.

#### SRS-FUN-20
Система повинна надавати ендпоінт перевірки підпису та статусу анулювання QR-коду.

### 2.6 Модулі `audit` та `notification`

#### SRS-FUN-21
Система повинна публікувати кожну зміну стану замовлення як подію через Transactional Outbox.

#### SRS-FUN-22
Система повинна записувати події змін станів замовлення та події безпеки в append-only журнал аудиту.

#### SRS-FUN-23
Система повинна надсилати email-сповіщення покупцю та продавцю при кожній зміні стану замовлення.

#### SRS-FUN-24
Система повинна приймати звернення щодо проблемного квитка через форму і надсилати користувачу email-підтвердження прийняття звернення.

#### SRS-FUN-25
Система повинна знеособлювати персональні дані облікового запису за запитом користувача із збереженням знеособлених записів журналу аудиту.

## 3. Non-Functional Requirements (Нефункціональні вимоги)

### 3.1 Продуктивність (PERF)

#### SRS-NFR-PERF-01
Час відгуку операцій читання (каталог подій, оголошення) має становити p95 ≤ 200 мс при навантаженні 200 RPS протягом 5 хв.

#### SRS-NFR-PERF-02
Час відгуку операції резервування має становити p95 ≤ 400 мс при 50 одночасних віртуальних користувачах протягом 5 хв.

#### SRS-NFR-PERF-03
Частка відповідей з кодами 5xx має становити < 1 % за навантаження, визначеного [SRS-NFR-PERF-01](#srs-nfr-perf-01).

### 3.2 Цілісність даних (INT)

#### SRS-NFR-INT-01
Кількість подвійних продажів має дорівнювати 0 у сценарії з 500 одночасними спробами резервування одного оголошення.

#### SRS-NFR-INT-02
Час життя резерву (TTL) має становити 10 хв; резерв має звільнятися не пізніше ніж через 60 с після завершення TTL.

### 3.3 Безпека (SEC)

#### SRS-NFR-SEC-01
Автентифікація має виконуватися за протоколом OpenID Connect (Authorization Code Flow з PKCE).

#### SRS-NFR-SEC-02
Access token має бути JWT з підписом RS256 і строком дії 5 хв; refresh token — зі строком дії 30 хв.

#### SRS-NFR-SEC-03
Двофакторна автентифікація для ролі SELLER має реалізовуватися за алгоритмом TOTP (RFC 6238).

#### SRS-NFR-SEC-04
Зовнішній трафік має передаватися лише через TLS 1.2 і вище з заголовком Strict-Transport-Security.

#### SRS-NFR-SEC-05
Ліміт запитів на IP-адресу має становити 20 запитів/с з ємністю bucket 40; перевищення має повертати HTTP 429 із заголовком Retry-After.

#### SRS-NFR-SEC-06
Ліміт запитів на резервування має становити 5 запитів/хв на обліковий запис.

#### SRS-NFR-SEC-07
Квота має становити не більше 4 квитків на обліковий запис для однієї події.

#### SRS-NFR-SEC-08
Обліковий запис має блокуватися на 15 хв після 3 перевищень ліміту [SRS-NFR-SEC-06](#srs-nfr-sec-06) протягом 10 хв.

#### SRS-NFR-SEC-09
QR-код має підписуватися алгоритмом ECDSA P-256 з SHA-256 (FIPS 186-5); закритий ключ має зберігатися поза Git-репозиторієм і передаватися в контейнер як секрет.

#### SRS-NFR-SEC-10
Звіти SonarQube, OWASP Dependency-Check, Trivy та OWASP ZAP (baseline scan) для гілки main мають містити 0 вразливостей рівнів Critical і High.

#### SRS-NFR-SEC-11
Git-репозиторій має містити 0 секретів (паролів, ключів, токенів) за результатами сканування Trivy (`--scanners secret`).

#### SRS-NFR-SEC-12
API має повертати заголовки X-Content-Type-Options, X-Frame-Options, Content-Security-Policy і приймати cross-origin запити лише з домену клієнтського застосунку (CORS allowlist).

### 3.4 Комплаєнс (CMP)

#### SRS-NFR-CMP-01
Система має зберігати лише персональні дані, необхідні для виконання угоди: ім'я, email, ідентифікатор облікового запису (GDPR, Закон України «Про захист персональних даних»).

#### SRS-NFR-CMP-02
Система не повинна зберігати та обробляти дані платіжних карток (вимоги PCI DSS виконуються на боці платіжного провайдера).

#### SRS-NFR-CMP-03
Обліковий запис бази даних застосунку не повинен мати прав UPDATE та DELETE на таблицю журналу аудиту.

### 3.5 Надійність (REL)

#### SRS-NFR-REL-01
Доставка подій з Outbox до RabbitMQ має виконуватися з інтервалом опитування ≤ 1 с і семантикою at-least-once; споживачі мають ігнорувати повторні події за ідентифікатором події.

#### SRS-NFR-REL-02
Обробка події має повторюватися до 3 разів з експоненційною затримкою; подія, що не оброблена після 3 спроб, має переміщуватися в Dead Letter Queue.

#### SRS-NFR-REL-03
За недоступності Redis резервування має виконуватися з оптимістичним блокуванням PostgreSQL без порушення [SRS-NFR-INT-01](#srs-nfr-int-01).

#### SRS-NFR-REL-04
Резервна копія PostgreSQL має створюватися щодоби; RPO ≤ 24 год, RTO ≤ 1 год.

### 3.6 Інфраструктура (INF)

#### SRS-NFR-INF-01
Усі компоненти мають розгортатися командою `docker compose up` з health checks та політикою перезапуску `unless-stopped`.

#### SRS-NFR-INF-02
Сумарне споживання пам'яті контейнерів у режимі навантаження [SRS-NFR-PERF-01](#srs-nfr-perf-01) має становити ≤ 3,5 GB.

#### SRS-NFR-INF-03
Конвеєр CI (GitHub Actions) має запускатися для кожного Pull Request і виконуватися не довше 15 хв.

### 3.7 Спостережуваність (OBS)

#### SRS-NFR-OBS-01
Метрики Spring Boot Actuator мають збиратися Prometheus з інтервалом 15 с; дашборд Grafana має відображати латентність p95, частку відповідей HTTP 429 та 5xx.

#### SRS-NFR-OBS-02
Логи застосунку мають записуватися у форматі JSON з ідентифікатором кореляції (correlation ID) для кожного запиту.

### 3.8 Якість коду (QLT)

#### SRS-NFR-QLT-01
Покриття рядків коду модулів `listing`, `order` і `ticket` модульними тестами має становити ≥ 70 % за звітом SonarQube; SonarQube Quality Gate має бути пройдено.

## 5. Glossary (Глосарій)

| Термін | Визначення |
|---|---|
| JWT (JSON Web Token) | Стандарт (RFC 7519) компактного токена, що містить набір тверджень (claims) про користувача і захищений цифровим підписом; перевіряється без звернення до сервера, що його видав |
| OpenID Connect (OIDC) | Протокол автентифікації поверх OAuth 2.0, за яким сервер ідентичності (Identity Provider) видає застосунку підписані токени з даними про автентифікованого користувача |
| Token Bucket | Алгоритм обмеження частоти запитів: bucket заданої ємності поповнюється токенами з фіксованою швидкістю, кожен запит витрачає токен, запит за порожнього bucket відхиляється |
| Race condition | Стан, за якого результат операції залежить від порядку виконання паралельних запитів; у домені — одночасне придбання одного квитка кількома покупцями |
| Transactional Outbox | Патерн, за яким подія записується в таблицю outbox у тій самій транзакції, що й зміна бізнес-даних, і публікується в брокер повідомлень окремим процесом |
| p95 Latency | Значення часу відгуку, яке не перевищують 95 % запитів за період вимірювання |
| ECDSA | Алгоритм цифрового підпису на основі еліптичних кривих (FIPS 186-5); підпис формується закритим ключем і перевіряється відкритим ключем |
